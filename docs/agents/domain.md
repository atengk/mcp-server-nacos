# 领域模型与架构文档规范 (Domain Docs)

本规范指导工程技能与智能体在探索、重构和开发本代码库时，如何正确理解和遵循业务概念与技术架构。

## 探索与编码前的必读顺序

1. **项目根目录 `CONTEXT.md`**：阅读全局领域术语、统一业务语言（Ubiquitous Language）与核心设计模型；
2. **架构决策记录 `docs/adr/`**：阅读与当前改动领域相关联的 ADR 记录。

> 💡 **静默兼容准则**：若上述文件尚不存在，**直接静默继续执行**，无需报错；相关文档将在触发 `/domain-modeling` 技能时按需补充。

## 目录结构标准 (单上下文工程)

```text
.
├── CONTEXT.md                 # 核心统一语言与领域术语词典
├── docs/adr/                  # 架构决策记录目录 (Architecture Decision Records)
│   ├── 0001-xxxx.md           # 架构决策历史
│   └── 0002-xxxx.md
└── src/                       # 核心业务实现源码
```

## 术语一致性红线

- 在生成代码标识符、测试名称、PR 标题或 Issue 描述时，**严禁自创新词**，必须严格遵循 `CONTEXT.md` 中已定义的术语词汇；
- 如果遇到未被定义的关键新概念，提示用户或作为待办事项记录，通过 `/domain-modeling` 技能统一收敛补充。

## 架构决策冲突显式暴露 (Flag ADR Conflicts)

如果新的设计或重构提议与既有 ADR 发生冲突，**严禁静默覆盖**，必须在方案中显式标出，例如：
> ⚠️ *“本方案与 ADR-0002 产生冲突，但基于以下理由建议重新讨论……”*
